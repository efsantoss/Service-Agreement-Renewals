Introduction

This document explains how the Upcoming Renewals solution is built: the architecture, each component and its responsibility, the data model, the design decisions and how to deploy and test it. The business behavior is described in the companion Functional Documentation.

Document status. Version 1.0 describes the delivered source code. Class names, queries and test results below match the repository.

Solution Architecture

Design principles

  • Separation of concerns. Each class has one reason to change.
  • Bulk first. Every public method receives and returns collections.
  • One query, one DML. SOQL lives in selectors; DML lives in services.
  • Business rules are data. The 30-day window and the 10-day lead are configuration.
  • Testable by design. Pure logic has no SOQL or DML, and the current date is injectable.
  • Secure by default. with sharing, user-mode queries and DML.

Validation rule End_Date_After_Start_Date rejects records where the End Date is earlier than the Start Date. The object has Allow Activities enabled so Tasks can reference it through WhatId.

Platform constraint: no custom fields on Task

The original design stored a unique key on the Task. Deploying any custom field to Task or Event in the target org fails with bad value for restricted picklist field: Task (verified with dry-run deployments; the same field on Account deploys fine). The duplicate-prevention marker therefore lives on the Service Agreement as Renewal_Task_Id__c. The Task is linked to the agreement through the standard WhatId.

Renewal_Setting__mdt

Field Default Purpose
Renewal_Window_Days__c 30 Size of the look-ahead window.
Task_Lead_Days__c 10 How many days before End Date the Task is due.

Trigger Architecture

Principles

  • One trigger per object, no logic inside it.
  • Runs after insert and after update, because the Task needs the agreement Id as WhatId, and the agreement is updated afterwards with the Task Id.
  • Operates on List<Service_Agreement__c>, never on a single record.
  • The Task is created in the same transaction, so a failure is visible to the user who saved the agreement.

Execution flow

  1. The trigger passes Trigger.operationType, Trigger.new and Trigger.oldMap to the handler.
  2. The handler calls RenewalTaskService.createRenewalTasks(agreements).
  3. The service keeps only agreements where RenewalEligibility returns true.
  4. One query in ServiceAgreementSelector re-reads the current state of those agreements with FOR UPDATE, including the Account Manager and its active flag, and keeps only those whose Renewal_Task_Id__c is empty.
  5. One query in RenewalTaskSelector finds Tasks that already exist for them (secondary check).
  6. Tasks are built only for agreements that still have no Task.
  7. All Tasks are inserted with a single DML using partial success.
  8. One DML then writes the new Task Ids to Renewal_Task_Id__c on the agreements. The handler ignores the follow-up trigger pass, because those agreements now have a Task.

Why not a Record-Triggered Flow?

A Flow can create a Task, but this requirement combines bulk duplicate detection, owner fallback, configurable date rules and boundary-condition tests. Apex keeps that logic explicit, unit-testable and easier to review. Declarative tools are still used where they fit best: object and field metadata, the validation rule, Custom Metadata and permission sets.

Date Handling

  • All values are Date (not Datetime), so time zones cannot shift a day.
  • Arithmetic uses Date.addDays(), which is calendar-aware. No manual month or leap-year logic exists.
  • RenewalClock.today() is the only source of the current date. Tests override it.
  • The window check is today <= endDate <= today + windowDays.
  • The due date is max(endDate - leadDays, today).
  • "Days Remaining" is today.daysBetween(endDate).

Duplicate Prevention

Duplicates are prevented in three complementary layers.

  1. Marker on the agreement. Renewal_Task_Id__c is written when the Task is created. An agreement with this field populated never receives another Task, no matter how often it is edited.
  2. Fresh read under lock. The service does not trust the possibly stale Trigger.new. It re-reads the agreements with FOR UPDATE and decides on the current database state, which serializes concurrent transactions on the same agreement.
  3. Secondary check on Tasks. One query on existing Tasks by WhatId covers agreements whose marker was cleared or loaded without it.

The marker is the Task Id, so changing the End Date later does not create another Task (a documented assumption). Repeated agreements in the same batch are collapsed by Id before processing.

Trade-off. A unique constraint in the database would be the strongest guarantee, but it cannot be placed on Task in this org (see Platform constraint). The three layers above give equivalent protection in practice, at the cost of one extra DML on the agreement.

Security

Each path declares its access model explicitly, according to who is acting.

Path Access model Reason
Upcoming Renewals (controller and UpcomingRenewalsService) with sharing, WITH USER_MODE queries, AccessLevel.USER_MODE DML A person is acting: object permissions, field-level security and sharing of that user are enforced. A user without access receives a friendly error instead of data.
Renewal Task automation (RenewalTaskService) without sharing, system mode The system is acting on behalf of the business whenever anyone saves an agreement (including integrations). It must see Renewal Tasks owned by other users and stamp the system-managed marker even when the editing user cannot edit that field.
Selectors inherited sharing Follow the caller, so the same query class serves both paths without changing their rules.
  • Access is granted by the Upcoming_Renewals_User permission set (object, fields, Apex class and tab). Profiles are not modified. Renewal_Task_Id__c is read-only in the permission set and on the layout.
  • All SOQL is static with bind variables. There is no string-built SOQL, so injection is not possible.
  • The controller returns UpcomingRenewalDto objects with only the displayed fields, never raw records.
  • startRenewalWork ignores Ids that do not belong to Service_Agreement__c.

Error Handling

Situation Handling
Task insert fails for some records Partial-success DML inside the service. Failures are returned to the handler, which calls addError on the originating agreement, so the user or integration sees why. Successful records follow the platform's save semantics (kept on partial-success saves, rolled back with the statement on all-or-none saves).
Task created but the agreement marker cannot be saved Reported on the agreement with addError, which rolls the statement back so no Task is left without its marker.
Inactive or missing Account Manager Handled by the owner fallback, never an exception.
Controller errors Caught and rethrown as AuraHandledException with a user-friendly message. The technical detail is logged.
Missing configuration record Safe defaults (30 and 10) are used.

Testing Strategy

Tests are designed around behaviors, not coverage numbers. Each test sets up its own data with RenewalTestDataFactory, pins "today" with RenewalClock and asserts on outcomes with a message that explains the expectation.

Results. 47 Apex tests in 5 test classes, all passing; 93% code coverage across the solution. 4 Jest tests for the component. Every deployment is validated with RunLocalTests before it is promoted.

Test class Focus
RenewalEligibilityTest Pure rules without DML: criteria, window edges, month, year and leap-year boundaries, configurable values.
RenewalSettingsTest Configured values, defaults for missing or invalid configuration, the deployed Default record, the clock.
ServiceAgreementTriggerTest End-to-end through DML: Task creation, non-qualifying records, duplicates, bulk, owner fallback, dates.
ServiceAgreementTriggerHandlerTest Failure path with the Apex Stub API: a Task failure is reported on the agreement.
UpcomingRenewalsControllerTest List content and order, DTO mapping, starting renewal work, security with and without the permission set.

Bulk 250 mixed records (200 qualifying, 50 outside the window) inserted and updated together; asserts 200 Tasks, at most 3 queries, and no extra queries on the update.

Deployment and CI/CD

Source control is the source of truth. Changes are validated before they are deployed, and the validated package is the one that is promoted. Target org alias: dev.

Recommended pipeline

  1. Static checks: ESLint, Prettier and LWC Jest.
  2. Validate (check-only) with tests: nothing is saved to the org.
  3. Quick deploy of the validated package.
  4. Post-deploy: assign the permission set and run a smoke test.

Commands

# 1. Static checks
npm run lint
npm run prettier:verify
npm run test:unit

# 2. Validate only, running all local tests (nothing is deployed)
sf project deploy validate --source-dir force-app --test-level RunLocalTests --target-org dev

# 3. Quick deploy using the job id returned by the validation
sf project deploy quick --job-id <validation-job-id> --target-org dev

# 4. Assign access
sf org assign permset --name Upcoming_Renewals_User --target-org dev

# 5. Optional: demo data (and its cleanup)
sf apex run --file scripts/apex/seed-demo-data.apex --target-org dev
sf apex run --file scripts/apex/delete-demo-data.apex --target-org dev

# Run Apex tests with coverage at any time
sf apex run test --test-level RunLocalTests --code-coverage --result-format human --target-org dev

Version control is handled manually by the developer. The pipeline above deploys to the Salesforce org only; the Git repository is never an automated deployment target.

Design Decisions

Decision Alternatives considered Rationale
Custom object Service_Agreement__c Contract, ServiceContract Standard objects do not allow editing Status and End Date and have no Renewal Required field.
Account Manager as Lookup(User) Account owner, Contact, text A Task owner must be a User, so the lookup gives the OwnerId with no conversion.
Owner fallback Skip Task; make the field required Never loses a renewal and never blocks saving.
Apex trigger, not Flow Record-Triggered Flow Bulk duplicate detection and boundary tests are clearer and testable in Apex.
Own lightweight handler fflib, Trigger Actions Framework No external dependency; same layering, easy to migrate to a framework later.
Marker Renewal_Task_Id__c on the agreement Unique key on Task; query-only check Task does not accept custom fields in this org. The marker plus a locked re-read closes the race condition that a query alone cannot.
Renewal Work Status on the agreement Task status; both Single source of truth on the managed record. The UI does not depend on a Task existing.
Settings in Custom Metadata Hard-coded constants Business can tune the window and lead time without a code deployment.
Task automation in system context User mode everywhere The automation must work for any user or integration that saves an agreement; user mode is kept for the paths where a person reads or changes data.
Idempotent service instead of a static recursion flag Static "already ran" Boolean Static flags skip records in bulk loads above 200 (the platform processes them in chunks in one transaction).

Limitations and Future Work

  • Evaluation happens when an agreement is saved. An agreement that is never edited will not receive a Task when it enters the 30-day window. A daily Schedulable and Batchable job reusing RenewalTaskService closes this gap.
  • Notifications (custom notification or e-mail) for new Renewal Tasks.
  • Synchronize the Renewal Task status with Renewal Work Status.
  • Index End_Date__c if data volume grows to large data volumes.
