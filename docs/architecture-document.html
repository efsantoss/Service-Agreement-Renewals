Introduction

Purpose

This Software Architecture Document (SAD) describes the architecture of the Upcoming Renewals solution from several viewpoints, and records why the main decisions were taken. The Functional Documentation explains what the solution does; the Technical Documentation explains how each piece is built. This document sits above both: it explains how the pieces fit together, which qualities the design protects, and which alternatives were rejected.

Scope

The solution lives entirely inside one Salesforce org. It has no external integrations. It covers the Service Agreement data model, the renewal rules, the automatic Renewal Task, the Upcoming Renewals Lightning Web Component, security, testing and the delivery pipeline.

Document status

Decisions in this document are final unless marked otherwise. Components still being implemented are labelled Planned and are reconciled with the final source code before submission.

Architectural Goals and Constraints

Business drivers

ID Requirement from the assessment
R1 An Apex service identifies agreements needing attention: Active, Renewal Required, End Date in the next 30 days.
R2 A trigger creates a Renewal Task for the Account Manager, due 10 days before End Date, never duplicated, bulk-safe.
R3 A Lightning Web Component named Upcoming Renewals lists them and lets users mark renewal work as started.
R4 Calendar-day arithmetic that is correct across month ends, year ends and leap years.
R5 Apex tests for qualifying, non-qualifying, bulk, duplicate, boundary and negative scenarios.

Constraints

Constraint Impact on the architecture
Salesforce governor limits Every path is bulk-first: queries in selectors, one DML per object per transaction, no loops that query or write.
No custom fields on Task or Event in the target org Verified with dry-run deployments (the same field deploys to Account but not to Task or Event). Duplicate prevention cannot use a unique key on Task and moves to the agreement (ADR-005).
Single org, Developer Edition No separate sandbox is assumed. Safety comes from check-only deployments and automated tests before every deploy.
No external dependencies No managed packages or Apex frameworks. Layering is implemented with plain classes (ADR-002).
Source control is the source of truth All metadata lives in Git. Changes reach the org through the Salesforce CLI from reviewed branches.
Three-day delivery window Scope is the required behavior plus the quality attributes below. Extras are listed as roadmap items.

Context View

The solution is a self-contained Salesforce application. People interact with it only through Salesforce.

Logical View

Layers and dependency rules

The back end is organized in layers. Dependencies point downward only, so a lower layer can be tested and changed without knowing who calls it.

Layer Members Planned Rules
Entry points ServiceAgreementTrigger, UpcomingRenewalsController No business logic. Translate the platform context (trigger or Aura call) into a call to a handler or service.
Handler ServiceAgreementTriggerHandler Decides what runs per trigger context. Passes whole collections.
Services RenewalTaskService, UpcomingRenewalsService Own the use cases and the transaction. The only layer that performs DML.
Domain RenewalEligibility Pure business rules. No SOQL, no DML, no static state. Receives all inputs as parameters.
Support RenewalSettings, RenewalClock Configuration access and the single source of "today".
Selectors ServiceAgreementSelector, RenewalTaskSelector The only place that contains SOQL, always in user mode. Never call services.

Why this shape

  • Testability: the domain layer is tested with plain objects and fixed dates, without the database.
  • Governor-limit control: because SOQL and DML are confined to selectors and services, the cost of any path can be counted by reading two classes.
  • Replaceability: the layering matches fflib-style conventions, so a framework can be adopted later without rewriting business rules.

Process View

Renewal Task creation

Step 9 re-fires the trigger on the updated agreements. The service ignores them, because Renewal_Task_Id__c is now populated, so the loop ends after one extra pass.

Upcoming Renewals component

Step Interaction
1 The component loads and calls a cacheable Apex method on UpcomingRenewalsController.
2 The controller calls UpcomingRenewalsService, which asks ServiceAgreementSelector for qualifying agreements (one SOQL in user mode).
3 The service computes Days Remaining and the controller maps the result to a DTO that exposes only the displayed fields.
4 The user selects rows and clicks Start Renewal. The component calls a second, non-cacheable method with the selected Ids.
5 The service sets Renewal_Work_Status__c to In Progress with one user-mode DML, returning per-record results.
6 The component shows a toast and refreshes the list. Errors become AuraHandledException messages.

Data View

State models

Field Lifecycle
Status__c Draft → Active → Expired, or Cancelled from Draft or Active. Only Active participates in renewal.
Renewal_Work_Status__c Not Started → In Progress. Independent of Status, so an agreement stays visible while it is being renewed.
Renewal_Task_Id__c Empty → populated once, by the system. Its presence means "a Renewal Task exists".

Security View

Concern Design response
Who may use the feature A dedicated permission set grants the object, field and Apex class access. Profiles are not modified (least privilege).
Record visibility All Apex runs with sharing. Queries use WITH USER_MODE, so sharing rules apply to the list the user sees.
Field-level security User-mode queries and DML enforce FLS. Users without access to Agreement Value do not receive it.
Data exposure to the browser The controller returns a purpose-built DTO, never raw SObjects.
Injection No dynamic SOQL built from strings. Inputs are bound variables or typed Ids.
System-managed field Renewal_Task_Id__c is written only by the service and is read-only on the layout.
Sharing model Public Read/Write on the object, so an Account Manager who is not the owner can still see and update the agreement they are assigned to renew. Documented as an assumption.

Deployment View

Delivery pipeline

  1. Branchfeature branch from main
  2. Local checkslint, Prettier, Jest
  3. Pull requestpeer review
  4. Validatecheck-only deploy and Apex tests
  5. Mergeinto main
  6. Deployto the org

Principles

  • Nothing reaches main directly. Every change travels in a branch and a pull request.
  • Validate before deploy. A check-only deployment with tests proves the change is deployable without touching the org.
  • Deploy exactly what was validated. The validated change set is the one promoted.
  • Small, targeted deployments. Deploy by source path so unrelated metadata is never overwritten.
  • The pipeline deploys to Salesforce only. Git operations are performed by the developer.

Quality Attributes

Attribute Scenario How the architecture responds
Scalability A data load saves 10,000 agreements. The platform processes 200 records per transaction. Each transaction stays within a fixed budget of queries and DML (next section).
Reliability The same agreement is saved twice in a row, or by two users at once. Marker field, a locked re-read and a secondary Task check yield exactly one Task.
Correctness An agreement ends on Mar 1 of a leap year. Date arithmetic is calendar-aware and a single clock supplies "today", so boundary cases are tested deterministically.
Security A user without access to Agreement Value opens the component. User-mode queries and a DTO built from permitted fields.
Maintainability The business changes the window from 30 to 45 days. One Custom Metadata value changes. No code release.
Testability A rule must be verified for 200 mixed records. Domain logic is pure; services receive a test data factory and an overridable clock.
Usability Nothing qualifies, or the call fails. The component shows an empty state or a clear error message instead of a blank screen.

Governor-limit budget (trigger path, 200 records)

Resource Expected use Platform limit and notes
SOQL queries 2 to 3 100 per transaction. Re-read of agreements, existing Tasks and, if needed, user data. Configuration comes from Custom Metadata, which does not count.
DML statements 2 150 per transaction. One insert of Tasks, one update of agreements.
DML rows at most 400 10,000 per transaction. Up to 200 Tasks plus 200 agreements.
Queries inside loops 0 Enforced by design: selectors are called once with a set of Ids.

Architecture Decision Records

Each record states the context, the decision and its consequences. All are accepted.

ADR-001: Custom object Service_Agreement__c

Accepted

Context. The assessment describes a "Service Agreement" with Status, End Date, Agreement Value and Renewal Required. Standard Contract and Service Contract were evaluated.

Decision. Create a custom object.

Consequences. Standard objects make Status and End Date derived or read-only and have no Renewal Required field, which makes the rules untestable and unmodifiable. The custom object costs some setup but gives full control and a clean contract for tests and the UI.

ADR-002: Layered Apex without a framework

Accepted

Context. The solution needs separation of concerns, bulk safety and testability, with a small codebase.

Decision. Thin trigger, handler, services, domain, selectors and a single controller, implemented with plain classes.

Consequences. No dependency on fflib or the Trigger Actions Framework and a smaller surface to explain. The conventions are compatible, so adopting a framework later is a refactor of wiring, not of business rules.

ADR-003: Apex trigger instead of Record-Triggered Flow

Accepted

Context. A Flow could create the Task declaratively.

Decision. Use Apex for Task creation. Use declarative tools for metadata, validation, configuration and access.

Consequences. Bulk duplicate detection, owner fallback and boundary-date tests are explicit and unit-testable in Apex. The cost is a developer, rather than an admin, maintaining the logic.

ADR-004: Business parameters in Custom Metadata

Accepted

Context. The 30-day window and the 10-day lead are business rules that can change.

Decision. Store them in Renewal_Setting__mdt, with safe defaults in code.

Consequences. Admins can tune behavior without a release. A missing record never breaks the feature.

ADR-005: Duplicate prevention marker on the agreement

Accepted · replaces the initial design of a unique key on Task

Context. The first design placed a unique external key on Task. Deploying any custom field to Task or Event fails in this org with bad value for restricted picklist field, while the same field deploys to Account.

Decision. Store the created Task Id in Renewal_Task_Id__c on the agreement, re-read agreements with FOR UPDATE before deciding, and keep a secondary check by WhatId.

Consequences. The marker is visible to users and reusable by the UI. There is one extra DML and a follow-up trigger pass that the handler ignores. A database-level unique constraint is not available, so correctness relies on the locked re-read and is covered by tests.

ADR-006: Account Manager as a User lookup with owner fallback

Accepted

Context. A Task owner must be a User. The Account Manager can be empty or inactive.

Decision. Lookup to User, optional. If empty or inactive, the Task goes to the agreement owner.

Consequences. No renewal is dropped and saving is never blocked. The assignee may occasionally not be the Account Manager, which is documented.

ADR-007: Date type and an injectable clock

Accepted

Context. Renewals use calendar days and must be correct around month, year and leap-year boundaries.

Decision. Use Date only, addDays and daysBetween for arithmetic, and a single RenewalClock as the source of today.

Consequences. No time-zone drift and no hand-written calendar code. Tests pin the clock, so boundary cases do not depend on the day the test runs.

ADR-008: One controller and a DTO for the component

Accepted

Context. The component needs flattened, display-ready data and one write action.

Decision. A single @AuraEnabled controller delegates to a service and returns a DTO.

Consequences. The UI is decoupled from the data model, exposes only permitted fields and has one place to translate exceptions into user messages.

ADR-009: Renewal Work Status stored on the agreement

Accepted

Context. Users must indicate that renewal work has started.

Decision. A dedicated picklist on the agreement, independent of Status and of the Task.

Consequences. A single source of truth on the managed record. The list does not depend on a Task existing and the agreement stays visible while in progress. Synchronizing the Task status is a roadmap item.

ADR-010: Branch, pull request and merge workflow

Accepted

Context. The repository is the submission and should show disciplined delivery.

Decision. All changes travel through feature branches and pull requests. Validation runs before merge; deployment follows merge.

Consequences. A reviewable history and a safe main branch, at the cost of a few extra steps.

Risks and Technical Debt

Risk Level Mitigation
An agreement entering the 30-day window is never saved again, so no Task is created Medium Roadmap: a daily scheduled batch reusing RenewalTaskService. Documented as a known limitation.
Marker cleared by an administrator or a data load Low The secondary check by WhatId prevents a second Task and the marker is restored.
No database-level uniqueness for Tasks Low Locked re-read plus tests for repeated and concurrent saves. See ADR-005.
Public Read/Write sharing exposes values to all users Low Field-level security on Agreement Value through the permission set, and sharing can be tightened later.
Single org with no staging environment Medium Check-only validation with tests before every deployment. Add a sandbox for production use.

Evolution Roadmap

  • Daily scheduled job (Schedulable + Batchable) to catch agreements that enter the window without being edited.
  • Notifications: custom notification or e-mail for new and overdue Renewal Tasks.
  • Task and agreement synchronization: mark the Task In Progress when renewal work starts.
  • Queue or team ownership as the fallback assignee instead of the record owner.
  • Reporting: dashboards on renewal value at risk and renewal conversion.
  • Framework adoption (fflib or Trigger Actions Framework) if the number of triggers grows.
